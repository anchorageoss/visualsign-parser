The Bitcoin module decodes Partially Signed Bitcoin Transactions (PSBTs) into VisualSign payloads: what is being spent, who is being paid, and the fee.

## Architecture overview

### Transaction model
- **Encoding**: BIP-174 PSBT version 0, supplied as base64 or hex (an optional `0x` prefix is accepted). PSBT v2 (BIP-370), v2-only fields in a v0 PSBT, and trailing bytes are rejected. Encoded inputs are capped at 4 MiB; the unsigned transaction must be at most 400,000 weight units (the final signed transaction may be larger).
- **UTXO model**: the PSBT carries the unsigned transaction plus per-input metadata (`witness_utxo`, `non_witness_utxo`, derivation paths, scripts).
- **Address encoding**: a PSBT does not name its network. Addresses are encoded for mainnet by default; `parser_cli` takes `--bitcoin-network` (`bitcoin`, `testnet`, `testnet4`, `signet`, `regtest`).

### Key components

The Bitcoin parser produces:
- `Address Encoding`, explicitly marked `transaction network unknown`: the chosen encoding does not establish the transaction's network. The enclave uses mainnet encoding; the CLI accepts the selection above.
- One expandable `Input N` per input: outpoint, address, script type, amount, and where the amount came from. A `witness_utxo`-only amount is also marked `claimed amount, unverified` in the preview subtitle.
- One expandable `Output N` per output: address (or the raw script for `OP_RETURN` and other non-address scripts), script type and amount.
- Multisig details inside an input or output when the PSBT carries a recognized script: `Multisig` (threshold, script kind), `Cosigner N` (key and origin), and for taproot the `Internal Key`.
- `Fee`, transaction `Version`, per-input `Sequence` (replaceability signaling and BIP-68 relative locks), and effective `Lock Time` when non-zero. Lock time distinguishes block heights from Unix timestamps and is marked inactive when all input sequences are final.

## What the parser can and cannot vouch for

The parser holds no keys. It checks what a PSBT can prove on its own and flags the rest.

| Situation | Behavior |
|---|---|
| `non_witness_utxo` does not hash to the prevout txid, or the output index is out of range | Rejected |
| `witness_utxo` disagrees with `non_witness_utxo` | Rejected |
| `redeem_script` does not hash to the prevout script | Rejected (BIP-174 signer check) |
| `witness_utxo` (without `non_witness_utxo`) for an input whose spent script is not a witness program, such as P2PKH | Rejected (BIP-174 signer check) |
| `witness_script` does not hash to the P2WSH script being spent (the prevout, or the `redeem_script` for P2SH-P2WSH) | Rejected (BIP-174 signer check) |
| Duplicate input outpoints, input/output values or totals above `MAX_MONEY` (21 million BTC), or outputs exceed the fully known input total | Rejected |
| Every input amount verified through its previous transaction, with only ALL / DEFAULT sighashes | `Fee` shown as an amount |
| Every input spends a taproot output and some amounts are known only from `witness_utxo`, with only ALL / DEFAULT sighashes | `Fee` shown as `X BTC (claimed; enforced by BIP-341 signature)`, not as a verified amount. A BIP-341 ALL / DEFAULT signature without ANYONECANPAY commits to every input amount, so a signature over a wrong amount is invalid on-chain, provided the signer computes the sighash from the PSBT's amounts (see below). |
| Any other input amount known only from `witness_utxo` | `Fee` shown as `unknown (claimed X BTC; unverified: ...)`. A segwit v0 signature commits only to its own input amount, so a wrong `witness_utxo` can hide a large fee. |
| An input has no UTXO data, or the PSBT has zero inputs | `Fee` shown as `unknown` |
| An output carries `bip32_derivation` or `tap_key_origins` | Displayed as an ordinary output. Derivation metadata alone cannot establish a change claim or ownership. |
| An input or output carries a `witness_script` (wsh, optionally P2SH-wrapped) or tap leaf scripts | If the script is bound to the output (script hash, or taproot commitment through the control block or tap tree) and matches `multi`/`sortedmulti` or `multi_a` with distinct keys, the threshold, cosigner keys and key origins are shown. Anything else is shown raw as `unrecognized script`. |
| Taproot multisig whose internal key is not the BIP-341 NUMS point | `Internal Key Warning: internal key can spend alone` |
| Input requests NONE, SINGLE, either mode with ANYONECANPAY, or an invalid sighash | Rejected: this preview requires a commitment to every displayed output. This also refuses the legacy out-of-range SINGLE constant-hash case. |
| Input requests ALL with ANYONECANPAY | Accepted with a `Sighash Type` field and `Fee` shown as `unknown (claimed X BTC; unverified: ...)`: every output is committed, but other inputs can change. |

Change verification (deriving a change key from an account xpub) needs wallet context the parser does not have, and belongs in the signer. The parser does not validate existing signatures or query the chain to confirm that inputs are unspent.

### What the signer must do

The preview is only as good as the signer's agreement with it. A signer pairing with this parser must:

- **Compute every sighash from the PSBT it previewed.** In particular, a taproot signer must take the BIP-341 prevout amounts and scripts from the PSBT's `witness_utxo` / `non_witness_utxo`, not from its own UTXO index or wallet. The `claimed; enforced by BIP-341 signature` fee relies on this: if the PSBT understates an input amount, a signature made over the PSBT's amounts is invalid and cannot be broadcast. A signer that substitutes the real amounts (Bitcoin Core does this when it signs inputs from its own wallet) produces a valid signature while the user was shown a wrong fee. Such a signer must instead refuse a PSBT whose amounts disagree with its own.
- **Enforce the PSBT's sighash requests.** Every displayed output is only committed to under ALL / DEFAULT (or ALL|ANYONECANPAY, which the preview flags).
- **Apply the BIP-174 signer checks itself.** The parser refuses the cases above, but the signer is what actually produces the signature.

## Using parser_cli

```bash
cargo run --bin parser_cli -- decode \
  --chain bitcoin \
  --bitcoin-network bitcoin \
  --output human \
  -t "$(cat chain_parsers/visualsign-bitcoin/tests/fixtures/synthetic-p2wpkh-single-sig.input)"
```

## Test vectors

Fixtures live in `src/chain_parsers/visualsign-bitcoin/tests/fixtures/`. The `bip174-*` and `bip371-*` files are copied from the test vectors in [BIP-174](https://github.com/bitcoin/bips/blob/master/bip-0174.mediawiki) and [BIP-371](https://github.com/bitcoin/bips/blob/master/bip-0371.mediawiki); the `synthetic-*` files are built by the test suite from the BIP-84/BIP-86 test-vector keys.

`tests/vectors_test.rs` replays every test vector from BIP-174, BIP-370 and BIP-371 (`tests/fixtures/vectors/bip_vectors.json`, extracted from the BIP text at a pinned commit). Invalid vectors and all PSBTv2 vectors must be rejected. The four valid BIP-174 vectors that a signer must refuse (a witness UTXO for a non-witness input, two `redeemScript` mismatches, and a `witnessScript` mismatch) must each be rejected for their specific reason. Every other valid vector is compared with rust-bitcoin's view of the same bytes. `tests/mainnet_test.rs` replays mainnet transactions checked against a block explorer, and `tests/regtest.rs` (requires `bitcoind`) builds, signs and mempool-accepts PSBTs with Bitcoin Core.

## Implementation details

The `bitcoin` dependency uses the C-based `secp256k1-sys` implementation; building this crate requires a C toolchain, including for Apple targets.
