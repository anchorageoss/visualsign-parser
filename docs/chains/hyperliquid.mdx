The Hyperliquid module ends blind signing of Hyperliquid L1 actions. An L1 action (an order, a cancel, a vault transfer, a deploy) is signed as an EIP-712 `Agent` struct that holds only `connectionId`, a keccak hash of the msgpack-encoded action. The typed data alone tells you nothing about what you are approving. The parser takes the typed data together with the action it claims to commit to, recomputes the hash, and refuses to render anything that does not match.

<Note>
`hyperliquid` is on by default in `parser_cli` only. In `parser_app`, `parser_http_server` and the container images it is opt-in: build with `--features hyperliquid`, or add `hyperliquid` to `CHAIN_FEATURES`.
</Note>

## Input format

The transaction string is one JSON document.

```json
{"kind":"l1","typedData":{...},"action":{...},"nonce":1761480000000,"vaultAddress":null,"expiresAfter":null}
```

```json
{"kind":"userSigned","typedData":{...}}
```

- `typedData` is the EIP-712 payload that gets signed.
- For `l1`, `action`, `nonce`, `vaultAddress` (`null` or a `0x` address) and `expiresAfter` (`null` or milliseconds) are the request fields the hash covers. Send `action` exactly as it will be posted to `/exchange`: key order matters.
- Inputs over 256 KiB, or nested deeper than 16 levels, are refused before parsing.

## L1 actions

### Verification

1. The domain, types and primary type must equal the pinned L1 envelope: `{name: "Exchange", version: "1", chainId: 1337, verifyingContract: 0x0}`, `Agent [source string, connectionId bytes32]`. `chainId` must be a JSON integer.
2. The parser transcodes the action's raw JSON to msgpack in received key order, then computes `keccak256(msgpack ‖ nonce u64 BE ‖ 0x00 | 0x01 ‖ vault ‖ [0x00 ‖ expiresAfter u64 BE])`, as `action_hash` does in the Python SDK. The result must equal `message.connectionId`.
3. `source` `a` is shown as Mainnet and `b` as Testnet. Any other value is refused.
4. The action is parsed into display structs that deny unknown fields. They are then re-encoded to msgpack and must equal the hashed bytes byte for byte, so what you see is exactly what was hashed.

Floats anywhere in the action are refused. Hyperliquid carries prices and sizes as strings.

### Supported action types

| `type` | Shown |
| --- | --- |
| `order` | Each order: asset, side, limit price, size, limit TIF or trigger (tp/sl, market/limit, trigger price), reduce-only, client order id; grouping; builder and fee |
| `cancel`, `cancelByCloid` | Asset and order id or client order id; `f` (fast) when present |
| `modify`, `batchModify` | Order being modified (oid or cloid) and the new order |
| `scheduleCancel` | Cancel-all time, or "unset" |
| `updateLeverage`, `updateIsolatedMargin` | Asset, leverage and margin mode; margin added or removed in USDC |
| `twapOrder`, `twapCancel` | Asset, side, size, minutes, randomize, reduce-only; TWAP id |
| `vaultTransfer`, `subAccountTransfer` | Direction, vault or subaccount, USDC amount |
| `spotDeploy` | `registerToken2`, `userGenesis`, `genesis`, `registerSpot`, `registerHyperliquidity`, `setDeployerTradingFeeShare`, `enableFreezePrivilege`, `freezeUser`, `revokeFreezePrivilege`, `enableQuoteToken`, `disableQuoteToken` |
| `perpDeploy` | `registerAsset`, `registerAsset2`, `setOracle`, `setFundingMultipliers`, `haltTrading`, `setMarginTableIds`, `setFeeRecipient`, `setOpenInterestCaps`, `setSubDeployers`, `disableDex` |
| `outcomeDeploy` (HIP-4) | Venue plus `registerStandaloneOutcomeFromTemplate`, `registerQuestionFromTemplate`, `registerAndAssociateNamedOutcomeFromTemplate`, `settleOutcome`, `settleQuestion2`, `setSubDeployers` |
| `activateOutcomeDeployer` (HIP-4) | `activate` with venue name, or `deactivate` |
| `noop` | Nonce invalidation |

Every L1 payload also shows the vault or subaccount it acts for, the nonce as a UTC timestamp, `expiresAfter` as a UTC timestamp, and the verified `connectionId`.

Prices, sizes and decimal amounts appear exactly as signed. Assets appear as `#<index>`. Mapping indices to symbols needs exchange metadata, which is planned for a later release.

### Refused

- Any other `type`, such as `multiSig` (use the dedicated multisig envelope below), `setReferrer`, `createSubAccount`, `CValidatorAction` or `usdClassTransfer` sent as L1.
- Unlisted sub-operations of the deploy families: `spotDeploy.setTokenAnnotation`, `spotDeploy.setDeployerLabel`, `perpDeploy.setFundingInterestRates`, `setMarginModes`, `setDeployerFees`, `setPerpAnnotation`, `insertMarginTable`, `star` (HIP-3\*), and `isStar` in a new DEX schema.
- An action whose typed re-encoding differs from the hashed bytes, for example `scheduleCancel` with `"time": null` (the SDK omits the key) or keys in a different order from the SDK.

## User-signed actions

User-signed actions are plain EIP-712 with readable fields. The domain must be `{name: "HyperliquidSignTransaction", version: "1", verifyingContract: 0x0}`; `chainId` is taken from the domain and shown as `Signature Chain ID`. Each primary type pins its exact field list:

| `primaryType` | Fields |
| --- | --- |
| `HyperliquidTransaction:ApproveAgent` | agent address, agent name, nonce; agent expiry from `valid_until <ms>` in the name, or a warning when there is none |
| `HyperliquidTransaction:TokenDelegate` | validator, wei, undelegate, nonce |
| `HyperliquidTransaction:Withdraw` | destination, amount, time |
| `HyperliquidTransaction:UsdSend` | destination, amount, time |
| `HyperliquidTransaction:SpotSend` | destination, token, amount, time |
| `HyperliquidTransaction:SendAsset` | destination, source and destination DEX, token, amount, from-subaccount, nonce |
| `HyperliquidTransaction:ApproveBuilderFee` | max fee rate, builder, nonce |
| `HyperliquidTransaction:UsdClassTransfer` | amount, to-perp, nonce |
| `HyperliquidTransaction:ConvertToMultiSigUser` | exact signers JSON, new members and threshold, or removal warning; nonce |

`hyperliquidChain` must be `Mainnet` or `Testnet`. The message may also carry the request's `type` and `signatureChainId`, which the SDK leaves in the dict it signs; they must agree with the primary type and the domain chain id. Any other field, or any other primary type, is refused.

## Example

```bash
cargo run --bin parser_cli -- decode --chain hyperliquid --output human \
  -t @src/parser/cli/tests/fixtures/hyperliquid-l1-order.json
```

```text
└─ Fields:
   ├─ Network: Testnet
   ├─ Action: Place Order
   ├─ Grouping: na
   ├─ Order 1
   │     Detail: Buy 0.0003 of #3 at 40200, Limit (Gtc)
   ├─ Acting For (Vault / Subaccount): None (signer's own account)
   ├─ Nonce: 2026-10-26 14:10:08 UTC (1793023808821)
   ├─ Expires After: Not set
   └─ Connection ID: 0xdc35b8a7...55b0a168 (verified against the action)
```

This fixture was recorded from a real testnet order. Change one byte of the action and the parser refuses it with `connectionId mismatch`.

## Native multisig requests

Native multisig uses a separate complete-action envelope. It does not accept a
hash-only request. The parser computes the native signing digest and verifies any
collected approvals; it does not sign, access wallets, query network membership,
or submit transactions.

```json
{
  "kind": "multisig",
  "role": "member",
  "network": "testnet",
  "signer": "0x1111111111111111111111111111111111111111",
  "multisig": {
    "address": "0x3333333333333333333333333333333333333333",
    "authorizedUsers": ["0x1111111111111111111111111111111111111111"],
    "threshold": 1
  },
  "leader": "0x1111111111111111111111111111111111111111",
  "action": {"type": "cancel", "cancels": [{"a": 0, "o": 123}]},
  "nonce": 1793023808821,
  "vaultAddress": null,
  "expiresAfter": null,
  "signatures": []
}
```

The addresses above are illustrative public values. Preserve the inner action's
SDK wire order, including omitted versus null fields. Monetary values remain
strings. An optional `signingDigest` checks a caller's expected digest against the
computed native digest; this is a consistency check, not evidence that the caller
or the supplied configuration is trusted.

- `conversion`: the original account signs `convertToMultiSigUser`; `multisig`
  and `leader` are null and no approvals are supplied.
- `member`: an authorized member reviews and signs the complete inner action,
  bound to the multisig account, leader, network and nonce.
- `leader`: the direct authorized member leader reviews the final envelope.
  Supplied signatures must recover distinct authorized members and satisfy the
  supplied threshold. The leader's digest commits to the assembled envelope.

The authorized member set and threshold are caller-supplied context. A successful
parse proves signature and payload consistency against that context, not current
on-chain authorization. The consuming signer must authenticate its locally pinned
configuration, match the requested signer to its key, enforce its own signing
policy, and sign the returned digest. The coordinator must independently check
current network membership before submission. API-wallet leaders are not supported
by this format.

Changes to membership and removal of multisig protection use a
`convertToMultiSigUser` inner action under the current quorum. Review must distinguish
the current configuration from the proposed one. Removing protection returns
HyperCore control to the original account key. Native multisig does not protect
the same address on HyperEVM; CoreWriter is unsupported for multisig users.

The underlying protocol is documented in the
[official Hyperliquid multisig guide](https://hyperliquid.gitbook.io/hyperliquid-docs/hypercore/multi-sig).

Rust consumers parse with `HyperliquidTransaction::from_string` (the `Transaction`
trait) and match `HyperliquidTransaction::Multisig(request)`. The request exposes
`signing_digest`, `member_digest`, `verified_signers`, `leader_action_json`, role, network, requested
signer, configuration and the validated inner action. Render that same parsed
request through `HyperliquidVisualSignConverter`. Do not substitute independently
constructed display fields or a digest supplied by a coordinator.

`ConvertToMultiSigUser` is also accepted by the existing `userSigned` typed-data
format. That format does not contain the original account identity, so the caller
must additionally reject a new member equal to the original account. The complete
multisig envelope checks this itself for initial conversion and membership updates.

For leader requests, `leader_action_json` contains the exact native `multiSig`
action JSON in SDK field order, with signature `r`/`s` normalized to minimal
lowercase hexadecimal quantities. Use those bytes when assembling the exchange
request. Do not reserialize through a sorted JSON map or submit padded signature
strings from the input envelope: that could change the action hash. Other roles
return no leader action. The coordinator still owns the outer signature, nonce,
vault/expiry envelope, membership refresh and explicit submission.

### Multisig verification

The follow-up includes 43 independent SDK-derived inputs/digests, exact native
leader-action comparisons and seven review snapshots. On 2026-10-26, the focused
crate suite passed all 70 tests both with default features and with default
features disabled. CLI integration (one test), opt-in parser-app registry coverage
(three tests), strict Clippy, formatting and an `aarch64-apple-ios` library check
also passed using Rust 1.94. The library-only normal/build dependency graph has no
C cryptography dependencies. No protocol/protobuf changes are required.

These checks do not establish full-workspace CI, a deployed attested parser,
physical-device acceptance or live multisig execution. Server enablement remains
opt-in as in the parent PR.
