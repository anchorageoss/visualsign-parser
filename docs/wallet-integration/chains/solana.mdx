title: Solana for Wallets
description: What a Solana wallet must do when it shows and signs an off-chain message the parser rendered

This page covers signing a Solana off-chain message (`signMessage`) with the parser's help. Transactions need nothing beyond the [chain-agnostic flow](../core-concepts/how-parsing-works). For the envelope format and what the parser refuses, see [Off-chain messages](/chains/solana#off-chain-messages).

## Request

Send the envelope as the transaction string, with the chain set to Solana:

```json
{"message": "Sign in to app.example.com\nNonce: 42", "signerAddress": "BxrKzfvmQYjgFUzQwiNErgJabbrdqp6Ggci7h7q86naT"}
```

`message` is the exact text the dApp asked to sign. `signerAddress` is the account the wallet will sign with.

## Response

`payload_type` is `SolanaMessage`, distinct from `SolanaTx`, so a wallet can tell a message from a transaction without looking at the fields. The title is `Solana Message`, and there are two fields, or three when the message is [flagged](#flagged-messages):

| Label | Field type | Value |
| --- | --- | --- |
| `Warning` | text | Only on a flagged message, and first (see [Flagged messages](#flagged-messages)) |
| `Message` | text | The message, escaped (see below) |
| `Signing Address` | address | `signerAddress`, as given |

## What the wallet must do

The parser's output is only as safe as the wallet's handling of it. Before signing:

1. **Bind the signing address to the selected account.** The parser checks only that `signerAddress` is a well-formed Solana address. It has no key to compare it with, and it accepts an off-curve address (a PDA) that no key can sign for. The wallet must check that the address shown under `Signing Address` is the account it is about to sign with, and refuse otherwise.
2. **Sign the original bytes of `message`.** Sign exactly the UTF-8 bytes of the `message` string from the request: not the envelope, and not the escaped text the parser displays.
3. **Show the text exactly as given.** The displayed message is percent-escaped so that distinct messages always look distinct: every byte outside printable ASCII, plus `%` and `\`, appears as `%XX`, and a space at either end or in a run appears as `%20`. Do not URL-decode it. `%0A` looks like URL encoding, and a wallet that decodes it brings back the line break that lets a message forge a second line on the signing screen (for example a fake `To:` row). The same goes for `%E2%80%AE`, a right-to-left override that would reorder the text.

## Refused messages

Some messages are refused with an error instead of a payload, because a signature over their bytes would authorize more than the text:

- **Exactly 32 bytes, not all ASCII letters and digits.** NEP-413, SEP-53 and TON Connect verifiers (NEAR Intents among them) check an ed25519 signature over a 32-byte SHA-256 digest, and a Solana wallet signs message bytes as they are, so such a message may be a digest another protocol accepts.
- **Bytes that are a serialized Solana transaction message.** A signature over them is a valid signature for that transaction.

A wallet should treat these errors as "do not sign", not fall back to showing the raw text.

## Flagged messages

A message can also be the signed bytes of a NEAR Intents WebAuthn (passkey) authorization. The Ed25519 WebAuthn check in NEAR Intents verifies the signature directly over `authenticator_data || sha256(client_data_json)`. It checks the flags byte, but not the relying-party hash or the origin. So a message of at least 69 bytes whose byte 32 passes that flags check can be such an authorization for a payload from the signer's NEAR account: a dApp can grind the last 32 bytes, a SHA-256 digest, until they look like text. No length or charset rule rules this out, so the 32-byte rule above does not cover it.

The parser flags these messages instead of refusing them, because ordinary text matches the shape often. A flagged message renders as usual, with a `Warning` text field first (and, in a build with the `diagnostics` feature, a `message::near_intents_webauthn_shape` diagnostic).

The trigger is a single bit pattern in byte 32, so about 3 in 8 messages of 69 bytes or more are flagged, typical sign-in text included. How to present the flag is the wallet's decision. A blanket "do not sign" on every flagged message would mostly fire on ordinary text and teach users to dismiss it. A dApp that wants its messages unflagged can make byte 32 fail the check, for example with an even byte such as a space, which leaves UP clear.

The flag covers the message path only. It says nothing about other signing paths, such as transactions.
